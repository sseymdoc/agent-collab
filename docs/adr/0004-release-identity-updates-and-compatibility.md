# ADR 0004：发行身份、组件清单、兼容范围与更新

日期：2026-11-12　状态：已采纳

## 背景

M2 的候选包只有“开发候选版 / 内部测试版”两种身份，两者的本机实例都叫 `cand`；没有更新通道，没有组件清单，桌面安装包覆盖升级会留下上一版的资源文件。M3 要把发行身份、组件关系、兼容规则和更新步骤定下来，并且不让测试身份、测试密钥或测试地址进入正式通道。

## 决定

1. **三种构建身份，构建时由 `AGENT_COLLAB_BUILD_KIND` 指定，运行时与流水线都按它核对。**

   | 身份 | 应用标识 | 实例 | 本机端口 | 凭据服务名 | 更新通道 | 验签公钥 |
   | --- | --- | --- | --- | --- | --- | --- |
   | `formal` 正式版 | `org.agent-collab.desktop` | 空 | 18669 | `agent-collab` | `stable`（缺省）、`preview` | 正式公钥 |
   | `candidate` 开发候选版 | `org.agent-collab.desktop.cand` | `cand` | 18769 | `agent-collab-cand` | `stable`（缺省）、`preview`，指向测试更新地址 | 测试公钥 |
   | `internal-test` 内部测试版 | `org.agent-collab.desktop.cand-internal-test` | `itest` | 18779 | `agent-collab-itest` | `internal-test`，只指向测试更新地址 | 测试公钥 |

   - 版本号：正式版不带预发布后缀；候选与内部测试版必须带。`automation` feature 只允许在内部测试版。
   - 内部测试版与候选版的实例、端口、服务名、凭据服务名都不同，可以在同一台机器上先后或同时存在，不争抢同一份本机部署。
   - 正式版的实例为空，与命令行安装的缺省前缀是同一份：桌面端在那里发现已有安装（包括现有的个人部署）时只报告，不接管、不替换身份；候选凭据不会被正式版读取（服务名不同）。导入、重新配对与接管既有部署都要用户在界面里明确操作。
   - 更新通道与公钥在构建时写进二进制，页面只能在本身份允许的通道之间切换。正式身份的构建如果带测试公钥、测试地址、`automation`、预发布版本号或不安全传输开关，流水线直接失败（`scripts/release_gate.py`）。

2. **一份产品发行清单描述一次发行的全部组件**（`product-manifest.json`，流水线从最终产物生成）：发行 ID（等于桌面版本号）、身份与通道、源提交与干净状态、构建时间；各平台的最低系统、产物文件名/大小/SHA-256、签名与公证状态；组件版本与摘要（桌面外壳、随包载荷、后台发行包、Python 运行时）；协议版本与 controller features、数据库 schema 范围与指纹；兼容范围、升级顺序与可回退范围；cargo features 与第三方许可文件。GUI 版本（semver，`0.3.0-dev.1`）与后台版本（PEP 440，`0.3.0.dev1`）各用各的写法，清单写明对应关系。清单由更新验签同一把私钥签名（`product-manifest.json.sig`）。

3. **版本比较按各自的语义规则**：桌面端用 semver（预发布标识按数字比较，`dev.10` 新于 `dev.9`）；后台用本项目接受的 PEP 440 子集（`X.Y.Z[{a|b|rc}N][.devN]`），不是字符串排序。普通检查只提供更高版本；回退走明确的回退流程（桌面端重新安装旧安装包；本机后台 `install --rollback`），不在检查里自动降级。

4. **兼容规则**：协议版本（`PROTOCOL_VERSION`）不同即不兼容；同一协议版本内按 features 判断。每个后台发行版声明它作为节点要求 controller 具备的 features、作为 controller 要求节点的最低版本；桌面端声明它要求 controller 具备的 features。升级顺序沿用“先节点、后 controller”。`agent-collab release compat` 用发行清单与目标 controller 的 `GET /client`（或节点的注册应答）给出接受、降级（缺哪些 features、哪些功能不可用）或拒绝。

5. **各角色的更新范围**：
   - 桌面端（任何角色）：Tauri 官方 updater 负责检查、下载、验签与安装桌面安装包；它只更新这台机器上的桌面外壳与随包载荷（运行时、本机助手、后台发行包），不升级远端 controller 或节点，也不改用户的官方 Codex / Claude CLI 及其配置。
   - 本机完整部署：桌面更新完成后，随包后台版本新于本机已安装的版本时，界面单独列出“本机后台可升级”，展示影响（运行中的任务与写回、需要排空与重启的组件），由用户触发；执行仍是安装器的事务（兼容检查 → 准备与排空 → 备份 → 切换 → 健康检查），期望状态不变，原本停用的组件保持停用。桌面更新本身不重启、不打断本机后台服务（服务从安装前缀运行，不从应用目录运行）。
   - 节点与远端 controller：在目标机器上用受管安装器更新（有桌面端的机器在本机界面里操作；无图形的机器用 `agent-collab install`）。不经当前连接给远端安装程序，不新增常驻的高权限代理。
   - 独立下载的后台发行包用发行签名验证来源：OpenSSH 签名（`ssh-keygen -Y sign`，命名空间 `agent-collab-release`），安装器按已固定的 `allowed_signers` 用 `ssh-keygen -Y verify` 核对（在私有临时副本上核对已读入的字节；Windows 用系统自带的 OpenSSH）；不信任同源未签名的哈希清单。桌面安装包随包的发行包也带签名，本机部署向导第一次安装时固定信任。

6. **更新是一条可恢复的持久操作**，步骤固定为 `compat → download → verify → prepare → backup → switch → health`，结果为 `done`、`failed`（切换前失败，旧版本继续可用）或 `pending`（需要处理）。桌面端的记录在应用数据目录 `updates/`，本机后台的记录在安装前缀 `update-journal.json`；下次启动按记录与实际激活版本对账，不靠猜。程序回退只在声明的 schema 范围内进行；恢复旧数据库是另一个操作（`controller restore`），不作为更新失败的自动补救。普通兼容升级走正常重启，不调用恢复或切换屏障。

7. **随包载荷有确定清单**：构建时为 `resources/` 生成 `payload.json`（逐文件 SHA-256），其摘要编进二进制；外壳在第一次使用助手之前核对，缺文件、内容不符或有清单外文件（例如上一版残留的模块）时拒绝启动助手并提示修复安装。Windows 安装器在复制文件前清空受管的 `resources/`，因此覆盖安装与更新不留旧模块；用户数据、凭据、项目与本机部署都不在应用目录里，不受影响。

8. **三把信任根分开**：平台代码签名（Windows Authenticode、macOS Developer ID 与公证）、更新签名（Tauri updater 的 minisign 密钥）、传输（HTTPS）。任何一项都不替代另外两项。测试密钥与隔离地址只用于联调，不进入正式身份的构建；正式密钥在托管与备份方案确定之后生成，不生成后丢弃。

## 兼容机制与退出条件

| 机制 | 用途 | 退出条件 |
| --- | --- | --- |
| 没有 `update-journal.json` 的安装前缀按旧方式处理 | 此前版本安装的本机部署可以直接升级 | 一次性：第一次经新安装器升级后写入 |
| 没有 `payload.json` 的构建不做载荷核对 | 开发构建（`cargo tauri dev`）与 M2 之前的包 | 发行流水线构建的包都带清单；`release_gate` 拒绝缺清单的发行包 |
| 还没有固定信任的前缀可以安装未签名的本地发行包（输出“未验证来源”）；固定信任之后要显式 `--allow-unsigned` | 开发环境与此前版本安装的部署 | 正式发行包都带来源签名，桌面端与安装文档只给出带签名的安装方式；前缀第一次带签名安装或升级时固定 `allowed_signers`，之后升级必须带签名。现有部署都完成生产迁移（M4）、固定了信任之后，未签名的首次安装改为必须显式 `--allow-unsigned` |

## 不做

自建更新服务器或供应链平台；字节级可复现构建；静默升级远端 controller 或节点；在产品更新里升级或配置官方模型 CLI。
