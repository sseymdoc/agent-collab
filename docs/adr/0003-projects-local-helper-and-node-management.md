# ADR 0003：项目与本机目录、本机助手、凭据后端、节点管理的控制主体

日期：2026-11-12　状态：已采纳

## 背景

ADR 0002 确定了单一产品线、桌面外壳加同一套页面、客户端授权和模型设置。在它之上，本机完整模式、项目与文件夹输入、成果写回和节点管理需要再定几件事：项目的本机目录属于谁、谁读写本机文件、CLI 的凭据放在哪里、哪些节点操作可以远程做、没有核实过的节点能力怎么对待。

## 决定

1. **项目记录在 controller，本机目录在各设备。** controller 保存 `project_id`、名称、默认策略、配置版本和最近的输入基线；一个项目在某台设备上对应哪个目录，是那台设备上的绑定，不上传、不在设备之间共享（一台机器上的绝对路径对另一台没有意义）。默认值的优先级是 任务 > 项目 > 工作区，受理时冻结所用的项目配置版本与工作区设置版本；草拟与提交之间任何一个变了都拒绝。归档保留全部历史，没有删除。（`docs/protocol.md` §13.1）

2. **本机文件工作只有一份实现，在 Python 核心里。** 扫描、排除、快照稳定性、冲突判断、写入与恢复在 `agent_collab/project.py`。CLI 直接调用；桌面外壳把同一份代码作为随包的本机助手运行。外壳不另写一套快照或应用规则，页面更不写。
   - 助手不访问网络、不接触客户端凭据：上传与下载由持有凭据的外壳完成，助手只在用户经系统对话框选定的目录里读写。
   - 目录只能经系统对话框进入外壳的绑定表；页面不能提供路径。
   - 输入的一致性靠三层：读取前后核对、读完后整体复核、上传时按内容哈希再核对。内容寻址保证改过的文件不会以旧哈希进入基线。不承诺时间点一致的文件系统快照。
   - 成果应用按“输入基线、成果、目录现状”三方比较，只动成果改过的路径；本机改过的算冲突，缺省整体不写。写入逐文件原子替换并带备份与日志，不是跨文件事务；中断后可核对、续写或回滚。

3. **成果的四个状态分开记录，只有完整写入才算已回写。** 有检查点、已发布、已下载、已应用到项目各自有据。应用是 controller 上的一条记录，写入前登记为 `started`，结束后如实上报 `applied`、`partial`、`conflict`、`failed` 或 `unknown`；任务的 `integrated` 只对应 `applied`。并发任务的成果应用到同一个目录时，后一次按自己的基线重新核对，前一次改过的文件成为冲突，不互相覆盖。（§13.3、§13.4）

4. **凭据存储规则。**
   - 桌面端：只用系统凭据存储，读写失败即报错，没有明文回退（同 ADR 0002）。
   - CLI 与 Agent：缺省同样用系统凭据存储（Windows 凭据管理器、macOS 登录钥匙串、Linux Secret Service）。文件后端是另一个明确的后端，给没有图形会话的部署用，必须在配对时显式选择（`--credential-store file` 或环境变量）；系统存储不可用时命令报错并说明选法，不会自行改用文件。
   - 文件后端的保护按实际访问权限核对，而不是按创建时的设置推定：POSIX 看属主与权限位，Windows 读回访问控制列表；每次读取凭据前都核对。
   - 两种后端的凭据都只有配对码授予的权限，可单独撤销；命令输出存放位置，不输出凭据。
   - 这取代 ADR 0002 第 4 条里“CLI 与 Agent 的凭据是文件”的表述。

5. **节点管理的控制主体。** 节点主动连接 controller，心跳是唯一的控制通道。
   - 经这条通道提供的管理都不切断它：暂停与恢复接单、排空并迁移、维护状态、退役、以及结构化的管理操作（重新探测登录与模型目录、按任务读取原始输出）。管理操作是带请求者、状态与时限的异步记录，种类是封闭集合；没有远程 shell，界面不操作远端进程。
   - 停止或启动整个节点服务不经 controller 下发。服务停下后心跳随之断开，经同一通道“远程启动”无从实现；把停止与启动两个命令都交给即将停止的节点并不构成闭环。这两个动作在节点本机进行（`agent-collab service`，或该机桌面端的本机服务面板）。
   - 若以后需要完整的远程启停，前提是另有一个在节点服务停止后仍然在线的管理主体（例如独立于 worker 的本机管理代理，或操作系统级的带外管理），并为它单独定义身份、权限与审计；在那之前不提供。
   - 节点退役是墓碑语义：记录与历史引用保留，凭据作废，退出调度、模型目录与能力统计。没有删除节点的操作。

6. **服务期望状态属于用户。** 在受管服务安装上，用户执行的“停止服务”记为有意停用；升级、回退和失败后的自动回滚都不启动它，直到用户执行“启动服务”。为切换版本而临时停止不改变期望状态。离线（`--no-service`）安装没有可启停的服务，不在此列。服务与登录的关系按平台不同：Windows 计划任务以交互令牌运行、macOS LaunchAgent，都是用户会话级的，注销后停止、登录后启动；Linux worker 是 systemd 用户服务，安装器缺省不启用 linger（启用后注销后与开机时也运行），受管的 Linux controller 是系统服务，不依赖登录。不为无人登录运行而提升整个应用的权限。

7. **未核实的能力缺省不使用。** 节点的模型目录只有在“最近成功取得、且未过期”或“沿用上次成功的目录、CLI 版本与 provider 未变、且未过期”时算已核实。目录未知或已过期的节点缺省不承接 Codex 任务；“未核实能力尝试”是公开的显式设置，受理时冻结在任务上并出现在调度解释里，开启后仍优先已核实的节点。旧版本节点（不上报目录）只按它历史上固定支持的组合处理。目录探测与执行使用同一个模型 provider，并在探测时读回核对。（§12.5）

8. **按连接指定信任的 CA。** 证书始终校验。连接可以在配对时指定一份 CA 证书文件，此后这条连接只信任它；这用于自建 CA 的部署。没有跳过证书或主机名校验的选项。

9. **切换所需的控制在 controller 里。** 普通提交是否开放由提交闸门决定；备份之后产生了什么由事件序号界定并可查询；需要让切换前签发的执行权全部失效时用切换屏障，普通的停止再启动不承担这个作用。（§13.9、`docs/migration.md`）

10. **三种构建身份。** 正式版；开发候选版（可对外试用，预发布版本号，独立的应用标识与实例名，不含自动化钩子）；内部测试版（在候选版上编译进自动化钩子，只用于自动化验证真实窗口，不对外分发）。界面与 `app_info` 如实标明。这细化 ADR 0002 第 7 条。

## 兼容机制与退出条件

| 机制 | 用途 | 退出条件 |
| --- | --- | --- |
| 没有 `credential_store` 字段的 CLI profile 按文件后端读取 | 此前版本配对的凭据继续可用 | 随 profile 保留；重新配对后即带该字段 |
| 设置与旧客户端：`PUT /settings/models` 的 `codex` 省略 `unverified_nodes` 时保持原值 | 不认识这一项的客户端保存设置时不改动它 | 所有受支持的客户端都发送该字段之后的下一个发行版移除 |
| 节点对不声明 `catalog_provenance` 的 controller 不发送 `provider`、把沿用的旧目录按 `unknown` 上报 | 允许先升级节点 | controller 升级之后的下一个发行版移除 |
| 没有 `desired` 的安装记录按当前自启动状态推断 | 升级此前安装的节点时保持它当时的启停状态 | 一次性：升级后写入安装记录 |
| `config.json` 的 `managed_coordinator` 与 `standby_profiles` 在没有经 API 保存协调设置时生效 | 现有部署升级后协调行为不变 | 该部署保存过协调设置之后，这两项只为未设协调模型的情况提供模型与 effort |

ADR 0002 表中“没有上报模型目录的节点按固定组合处理”一项的退出条件，统计对象是仍参与运行的节点：已排空且不可达、或已退役的节点不要求上报目录。

## 后果

- 目录未知的新节点在取得目录之前不会被派 Codex 任务；首次配置要引导用户完成官方 CLI 的登录并用节点探测确认。
- 清单随请求内联提交，受单次请求上限约束（缺省约一万余个文件）；更大的项目要先调整排除规则或上限。
- 应用到项目需要已发布的成果；未发布的结果只能下载到别的目录查看。
- controller 与心跳通道不能启动一台已停止服务的节点；在节点本机（或经已有的 SSH 管理入口）执行 `agent-collab service start` 仍可以。界面与文档如实说明。
