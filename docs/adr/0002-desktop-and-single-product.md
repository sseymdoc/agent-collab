# ADR 0002：桌面端、统一入口与单一产品线

日期：2026-11-11　状态：已采纳

## 背景

- 目标产品是随仓库分发的 Windows / macOS 桌面软件，面向一个拥有者、多台设备的自托管部署。现有部署在该产品完整交付后迁入，之后只维护这一套。
- 现状（ADR 0001）：Python 标准库的 controller 与节点 agent，SQLite + 内容寻址 blob，React 看板经浏览器 Cookie 访问，自动化经管理令牌调用 API。
- 此前 Codex 的模型与 effort 写死在契约校验、修复派生、协调决策 schema 和适配器里；没有独立的客户端凭据，也没有按操作区分的权限。

## 决定

1. **一条主线，一套协议和状态机。** 不建个人分支或并行的个人流程。部署之间的差异只通过四样东西表达：部署配置（`config.json`）、controller 保存的设置、节点上报的能力、客户端的权限。域名、主机名、路径、凭据不进公共默认值。

2. **桌面端是 Tauri v2 外壳加同一套 React 页面。** 外壳（Rust）只保管客户端凭据、代发请求、转发事件流、把工件存到用户选定的位置（`docs/desktop.md`）。调度、发布、写回规则只在 controller；桌面端不读写数据库，不向节点发命令。页面在浏览器与桌面端共用，差别只在 `ui/src/transport.ts` 一层。

3. **桌面端、CLI 与其他 Agent 共用同一组 API 和同一个授权模型。** CLI（`agent-collab submit / job / baseline / settings / client`）是这组 API 的薄封装，不含调度、恢复或模型启动逻辑。契约的模板展开在 controller（`POST /contracts/draft`），界面和 CLI 都不拼装契约。

4. **客户端凭据独立于节点凭据和管理令牌**（`docs/protocol.md` §12.1）。
   - 客户端用 controller 本机签发的一次性配对码换取自己的凭据；权限分 `read`、`tasks`、`settings`、`devices`、`maintain` 五项，在每个路由上由 controller 检查；可单独撤销，撤销不影响节点和其他客户端。
   - controller 只保存凭据的哈希。桌面端把凭据放在系统凭据存储（macOS 钥匙串、Windows 凭据管理器），存储不可用时报错，不落明文；页面拿不到凭据。
   - CLI 与 Agent 的凭据是当前用户配置目录下仅本人可读写的文件，与节点凭据的保管方式相同。原因：自动化常在没有图形会话的环境里运行（例如经 SSH），那里读不到钥匙串；这类凭据按配对码授予的权限受限，并可单独撤销。
   - 每条连接绑定配对时的 `controller_id`；应答带 `X-Controller-Id`，不一致即停止使用该连接。
   - 管理令牌保留为 controller 本机的运维凭据，不分发给桌面端或自动化。

5. **模型与 effort 是设置，不是代码常量**（§12.3–12.5）。
   - 工作区默认值与部署许可范围保存在 controller，带 revision、并发冲突检查和修改记录；Codex 执行与 Claude 协调各自一组。
   - 任务受理时把 model、effort 解析成确定值写进契约，并记录请求值、解析值与来源；之后修改设置不影响已受理的任务。
   - 根工作包受理时冻结模型策略。后续修订与受管修复只读冻结值：模型不变，effort 只能在冻结的许可范围内改。
   - 可选组合是部署许可范围与节点上报目录的交集。目录由节点在自己的服务进程上下文里向本机 CLI 询问得到（Codex：`app-server` 的 `model/list`，经 stdio）；目录条目不代表该账号已成功调用。解析不出或不被允许时拒绝，不替换成别的组合。
   - 不修改用户的 Codex `config.toml`；执行参数随契约显式传给 CLI。

6. **节点主动连接 controller**，不要求节点开放入站端口；节点侧管理操作（服务启停、升级、登录引导）需要的远端管理 API 列入后续里程碑，不用原生桥执行远程命令代替。

7. **候选版与正式版分开。** 开发候选包使用独立的应用标识（`org.agent-collab.desktop.dev`）和预发布版本号，未签名，界面上标明不是正式发行版。

## 兼容机制与退出条件

| 机制 | 用途 | 退出条件 |
| --- | --- | --- |
| 浏览器控制台（`POST /session`、Cookie、静态页面），由 `web_console` 配置开关控制 | 迁移期间现有部署继续可用 | 桌面端与 CLI 覆盖日常操作并完成生产迁移后，在该部署设 `web_console: false`；之后的发行版移除静态页面的分发 |
| 节点接受旧的协调决策 schema（effort 必填、三个固定值） | 允许先升级节点、后升级 controller | controller 升级到带 §12 的版本之后的下一个发行版移除 |
| 没有上报模型目录的节点按固定组合处理 | 旧版本节点升级前仍能领取它本来就能跑的任务 | 所有未排空的已登记节点都上报目录（预检的 `nodes_declare_models`）之后的下一个发行版移除 |
| 升级前的数据库启动时写入一次模型设置迁移值 | 现有部署升级后行为不变，再由拥有者在设置里调整 | 一次性动作；写入后与普通设置无区别 |
| 没有冻结策略的旧根工作包按原固定组合推导 | 升级前创建的任务及其修复保持原行为 | 历史数据的读取规则，随数据保留；新建的根都有冻结策略 |

## 不做

托管服务、计费、多租户团队管理、完整 IDE、插件市场；任意需求的自动拆解、实时工具审批、交互式会话接管。

## 后果

- `validate_contract` 不再给 Codex 契约补默认模型：受理路径之外构造 Codex 契约必须显式给出 model 与 effort。
- 新部署在拥有者设置默认模型之前，提交不指定模型的 Codex 任务会被拒绝（`model_default_unset`）。
- controller 与节点的升级顺序是先节点、后 controller（见 `docs/migration.md`）。
